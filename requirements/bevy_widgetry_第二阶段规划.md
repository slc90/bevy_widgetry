# Bevy Widgetry 第二阶段规划

## 1. 第二阶段定位

第二阶段不再预设为“继续扩展控件和功能”的单一路线，也不提前限定统一主题。

这一阶段会同时处理工程化、公共 API、构建成本、控件扩展、控件对外交互，以及开发过程中临时出现的各种问题。具体工作按实际需要推进，不要求所有内容都提前可预测。

总体原则：

- 不为了“阶段完整性”提前制造任务；
- 真实遇到的问题优先；
- 需要工程化的地方就工程化；
- 需要新增控件时按实际需求逐个实现；
- 有值得尝试、值得探索、单纯觉得有趣的东西，也可以纳入本阶段。

---

## 2. 第二阶段需要解决的问题

### 2.1 Codex 工程化协作

后续开发会大量使用 Codex，因此需要建立一套适合长期协作的工程环境，使 Codex 能稳定理解项目、遵守项目约束、完成验证，并让经验持续沉淀到仓库中。

这个问题单独作为一个 Stage 处理。

### 2.2 公共 API 与接口规则

第一阶段允许较自由地调整内部结构和公开接口。

第二阶段开始，公共 API 不再默认“随便改”。需要明确哪些内容属于真正的公共接口，哪些只是实现细节，并整理第一阶段遗留下来的公共 API。

项目不专门维护复杂的 API 演进或兼容策略。需要修改时可以直接修改，之后遵守已经确定的规则即可。

### 2.3 工程瘦身与构建成本控制

当前工程的编译时间、测试成本和构建产物体积已经明显增长，例如完整 `cargo test` 可能产生非常大的 `target` 内容。

第二阶段需要正式处理这些问题，使构建成本变得可理解、可控制。

同时，既然已经有长期维护的 Widget Gallery，后续不再以 `examples` 作为控件展示与试用入口。

### 2.4 按实际需求补充控件

这个库主要供自己使用，因此不追求补齐其他 UI 库中的“常见控件全集”，也不根据外部组件表决定实现顺序。

到具体 Stage 时，根据实际需求一个一个实现需要的控件即可。

### 2.5 控件输入 / 输出语义与对外交互接口的一致性

随着控件数量增加，需要逐步梳理：

- 外部怎样驱动控件；
- 用户操作后控件怎样通知外部；
- 用户交互与程序更新如何区分；
- 相同语义在不同控件中如何保持一致。

这一阶段不预设必须采用总线、binding、callback 或其他某一种机制。

目标只是让不同控件的对外交互逐渐使用一致的表达方式。

### 2.6 Bevy 上游同步原则

项目长期遵循：

> Bevy 每发布一个新版本，无论大小版本，都跟进升级。

项目直接使用当前 Bevy 版本中合理的 API，不为了未来版本提前设计额外隔离层。

### 2.7 Ad hoc / Exploration

为无法提前分类的问题和自由探索保留正式空间。

这里既可以处理工程与体验问题，例如：

- 全局 UI 缩放；
- DPI / 高分屏；
- 字体；
- 窗口行为；
- 输入细节；
- 平台差异；
- Bevy UI 的具体限制。

也可以做并非“必要功能”的事情，例如：

- 小实验；
- 新交互尝试；
- 开发工具；
- 视觉或体验调整；
- 对 Bevy UI 某项能力的验证；
- 单纯觉得有趣、值得做的东西。

不要求这一部分有严格、统一的产出目标。

## 3. Stage 规划

### Stage 9：Codex 工程化

#### 目标 1：建立工程规范

建立适合项目长期维护的工程规范，用于约束后续人工开发与 Codex 开发。

规范覆盖项目真正需要统一的工程、代码、架构和质量要求。

#### 目标 2：建立项目文档体系

逐步建立能够长期维护的项目文档，包括：

- 项目整体结构；
- 各 crate / 模块职责；
- 重要设计决策；
- 公共 API 与行为语义；
- Stage 方案与实现背景；
- 需要长期保留的项目知识。

#### 目标 3：让 Codex 能稳定获取项目上下文

让项目中的规范、文档、架构和重要约束能够被 Codex 稳定找到和使用。

目标不是每次任务都重新解释整个项目，而是让仓库本身成为 Codex 的主要上下文来源。

#### 目标 4：建立自动验证体系

让 Codex 完成修改后能够执行可靠的自动验证。

验证范围按项目实际情况覆盖：

- 编译检查；
- lint / format；
- 单元测试；
- integration test；
- visual regression；
- 其他后续加入的自动检查。

#### 目标 5：建立 Review / 修改控制机制

让 Codex 的改动范围清晰、diff 易于审查，并避免无关修改和不必要的大范围重构。

重要架构与公共 API 决策仍然由人工最终确认。

#### 目标 6：建立反馈沉淀机制

Codex 在开发过程中出现的典型错误、踩过的坑、遗漏的约束，不依赖后续反复口头提醒。

根据问题性质，把经验沉淀到：

- 工程规范；
- 项目文档；
- 测试；
- 自动检查；
- 工具或脚本。

使项目逐渐变成一个越来越适合 Codex 长期工作的工程环境。

---

### Stage 10：工程瘦身与构建成本控制

#### 目标 1：定位构建膨胀来源

分析当前工程构建成本的主要来源，包括：

- 依赖；
- Bevy features；
- 测试；
- visual regression；
- GPU 相关能力；
- Gallery；
- workspace 结构；
- 其他重型构建路径。

先明确成本从哪里来，再决定如何优化。

#### 目标 2：降低普通开发路径的成本

让日常修改和验证尽量不必承担整个工程最重的构建成本。

普通开发路径应该尽可能快速、直接。

#### 目标 3：控制依赖与 Feature

整理不必要的依赖和 feature。

避免某个重型能力被无条件传播到所有 crate 和所有测试路径。

#### 目标 4：优化测试构建结构

区分快速验证与完整验证。

单元测试、集成测试、GPU / visual regression 等不同成本的测试，不应默认全部绑定在最普通的开发循环里。

#### 目标 5：清理并停止维护 examples

既然已经有 Widget Gallery：

- 后续不再新增控件展示类 `examples`；
- 现有展示用途逐步迁移到 Gallery；
- 删除不再需要的 examples；
- Gallery 作为统一的控件展示、交互试用和人工集成验证入口。

---

### Stage 11：按实际需求补充控件

根据真实使用需求，一个一个补充新的控件。

不提前追求控件数量，也不维护完整控件清单。

每个控件继续遵循现有项目方式：

```text
研究 Bevy 当前已有能力
        ↓
优先组合 / 扩展官方能力
        ↓
需要时设计自己的行为
        ↓
测试
        ↓
Style
        ↓
Theme
        ↓
Gallery
```

具体做哪些控件、采用什么顺序，到进入这个 Stage 时按实际需求决定。

---

### Stage 12：控件输入 / 输出语义统一

#### 目标 1：梳理现有控件的输入方式

检查外部如何：

- 设置控件值；
- 更新控件状态；
- 设置 disabled 等状态；
- 执行程序侧更新。

#### 目标 2：梳理现有控件的输出方式

检查用户交互之后，各控件如何把变化通知给外部。

#### 目标 3：统一相同语义的表达

逐步统一不同控件中重复出现的语义，例如：

- 用户交互；
- programmatic update；
- value change；
- 状态改变；
- disabled 情况下的行为。

不要求预先采用某一种固定机制。

#### 目标 4：把统一规则落实到现有和后续控件

先整理已有控件，再让后续新增控件直接遵守已经确定的规则。

最终目标：

> 让不同控件对外使用同一种“语言”。

---

### Stage 13：Ad hoc / Exploration

这个 Stage 保持开放，不预设固定任务清单。

可以处理：

- 开发过程中突然出现的工程问题；
- UI / UX 细节；
- 全局 UI 缩放；
- DPI；
- 字体；
- 窗口行为；
- 输入问题；
- 平台差异；
- Bevy UI 的实际限制；
- 临时需要的小工具。

也可以进行与当前主线无关但值得尝试的探索：

- 有趣的小实验；
- 新交互；
- 新视觉效果；
- 开发体验改进；
- Bevy 某项能力验证；
- 其他临时想到并且想做的东西。

原则是：

> 想到什么，只要觉得有价值、有趣、值得试，就可以做。

这个 Stage 不要求严格产出，也不要求所有工作都能归类为“功能开发”。

---

## 4. 当前第二阶段结构

```text
Stage 9
Codex 工程化
→ 规范
→ 文档
→ 上下文
→ 自动验证
→ Review
→ 反馈沉淀

Stage 10
工程瘦身
→ 定位构建成本
→ 优化普通开发路径
→ 控制依赖 / Feature
→ 优化测试构建结构
→ examples 迁移到 Gallery

Stage 11
按实际需求补充控件
→ 一个一个实现真正需要的控件

Stage 12
控件输入 / 输出语义统一
→ 梳理输入
→ 梳理输出
→ 统一相同语义
→ 应用于现有与后续控件

Stage 13
Ad hoc / Exploration
→ 处理无法提前分类的问题
→ 自由探索有价值或有趣的方向
```

---

## 5. 长期原则

### Bevy 版本跟进

```text
Bevy 发布新版本
        ↓
项目跟进升级
```

无论大小版本，都保持同步。

### 控件选择

```text
自己实际需要
        ↓
才决定是否实现
```

不以“控件库完整度”为目标。

### 第二阶段工作方式

第二阶段允许不同性质的工作同时存在。

既可以进行严肃的工程治理和 API 整理，也可以继续扩展控件，还可以处理突然出现的问题或单纯有趣的实验。

不为了规划整齐而限制项目实际发展。
