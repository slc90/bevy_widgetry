# Stage 10 工程瘦身与构建成本调查总结

## 1. 目标

Stage 10 原本计划处理工程瘦身与构建成本问题，重点包括：

* 定位构建产物膨胀来源；
* 调查 Bevy feature 是否存在明显冗余；
* 评估开发期编译速度优化空间；
* 清理不再需要的 `examples`；
* 判断是否有必要调整测试或构建结构。

本次调查最终重点聚焦于：

> 在尽量保留完整开发与调试能力的前提下，判断当前工程是否存在值得实施的构建体积或编译速度优化。

---

## 2. 构建产物体积调查

最初工程 `target` 目录约为：

```text
8.60 GB
```

进一步分析发现几乎全部来自：

```text
target/debug
```

一级目录占用：

```text
deps         6.59 GB
incremental  0.31 GB
build        0.10 GB
.fingerprint 0.00 GB
examples     0.00 GB
```

因此可以排除：

* incremental cache 是主要膨胀来源；
* build script 输出是主要膨胀来源；
* examples 独立输出目录是主要膨胀来源。

真正的主要成本集中在：

```text
target/debug/deps
```

---

## 3. deps 组成分析

按文件类型统计：

```text
Extension Count   GB
--------- -----   --
.rlib       327 4.45
.pdb         29 1.41
.rmeta      327 0.53
.exe          1 0.13
.dll         28 0.06
```

主要占用来自：

```text
.rlib   4.45 GB
.pdb    1.41 GB
```

其中最大的 `.rlib` 主要来自：

* `windows`
* `bevy_ui`
* `bevy_sprite_render`
* `bevy_render`
* `ash`
* `bevy_core_pipeline`
* `bevy_reflect`
* `bevy_camera`
* `bevy_ecs`
* `bevy_ui_widgets`
* `wgpu`
* 以及其他 Bevy 图形、UI、字体与平台相关依赖

没有发现某一个异常巨大的单独 crate。

整体表现更接近：

> Bevy UI + render + wgpu + Windows 平台依赖以及完整调试信息共同累积形成的大型构建产物。

---

## 4. Debug Info 实验

为了确认调试信息对体积的影响，临时关闭：

```text
CARGO_PROFILE_DEV_DEBUG=0
CARGO_PROFILE_TEST_DEBUG=0
```

重新构建后：

```text
.rlib   4.45 GB -> 1.76 GB
.pdb    1.41 GB -> 0.27 GB
.rmeta  0.53 GB -> 0.53 GB
```

仅 `deps` 就减少约：

```text
3.83 GB
```

因此可以确认：

> 完整 debug info 是当前构建产物体积最大的可调节因素之一。

但是项目开发过程中希望尽可能保留：

* 完整 panic / backtrace 调试能力；
* debugger 断点与单步调试；
* 局部变量观察；
* 对 Bevy / wgpu 等第三方库的调试能力；
* 尽量接近源码执行顺序的调试体验。

因此最终决定：

> 不通过降低 debug info 等级换取磁盘空间。

继续保持完整开发期调试信息。

---

## 5. Bevy Feature 裁剪实验

当前 Bevy 使用：

```toml
bevy = {
    version = "=0.19.1",
    default-features = false,
    features = ["ui"]
}
```

调查发现 Bevy 的 `ui` feature 会带入多个 UI、渲染、Picking 与平台相关能力。

曾尝试裁剪部分目前没有直接用途的 feature，例如：

```text
mesh_picking
sprite_picking
```

但实际重新构建后：

> 构建产物体积几乎没有明显下降。

同时：

```text
scene
```

虽然目前不是主要功能依赖，但后续计划使用 Bevy BSN，因此明确保留。

结论：

> 在当前 Widgetry 所需的 UI / render / picking / scene 能力范围内，继续细分 Bevy feature 的实际收益非常有限。

没有必要为了少量空间收益增加 feature 配置复杂度。

## 6. examples 清理

随着 Widget Gallery 已经成为长期维护的统一演示与人工集成验证入口，原有 `examples` 不再承担主要展示职责。

现有 examples 已手动清理。

后续原则：

* 不再新增展示型 examples；
* Gallery 作为统一控件展示入口；
* Gallery 作为交互试用入口；
* Gallery 作为人工集成验证入口。

这项调整主要用于减少维护负担和无意义构建目标，而不是作为解决 `target` 大小的主要手段。

## 7. 编译速度调查

### 7.1 rust-lld

当前 Windows MSVC 环境已经使用：

```toml
[target.x86_64-pc-windows-msvc]
linker = "rust-lld.exe"
```

因此较常见的链接器优化已经存在，无需调整。

### 7.2 Incremental Compilation

Cargo 开发期本身已经使用 incremental compilation。

当前工程：

```text
target/debug/incremental ≈ 0.31 GB
```

占用并不异常，也不是主要磁盘问题。

Incremental compilation 对日常局部修改有直接价值，因此继续保留。

### 7.3 第三方依赖高优化等级

Bevy 常见开发配置会使用类似：

```toml
[profile.dev]
opt-level = 1

[profile.dev.package."*"]
opt-level = 3
```

这可能改善运行性能，并配合某些 dynamic linking 开发模式。

但高优化等级会导致：

* debugger 单步行为与源码不再完全一致；
* 变量可能被消除；
* 函数可能被 inline；
* 调试第三方库体验下降。

项目明确选择：

> 开发期优先保证调试质量，而不是通过高优化等级追求编译或运行性能。

因此不采用这类配置。

### 7.4 Dynamic Linking

Bevy 支持开发期 dynamic linking，可以减少部分重复链接成本。

但 Windows 环境下一般需要配合较高依赖优化等级，同时增加开发配置复杂度。

由于当前项目优先保留高质量第三方库调试体验，因此不采用。

### 7.5 sccache

调查了 `sccache`。

它可以缓存 Rust 编译结果，对以下场景比较有效：

* `cargo clean` 后重建；
* CI；
* 多 workspace 共享依赖；
* target 被删除后的冷构建。

但当前项目日常开发主要依赖 Cargo incremental compilation，而 incremental crate 本身并不是 sccache 最适合的缓存对象。

同时 sccache 还会额外占用一份本地缓存空间。

因此它本质上属于：

> 用额外磁盘空间换取部分冷构建时间。

这与 Stage 10 当前的磁盘成本问题并不匹配。

最终决定：

> 暂不引入 sccache。

---

## 8. 最终结论

经过实际测量和实验，没有发现 Widgetry 工程自身存在明显错误或异常构建结构。

当前大型 `target` 主要来自：

```text
Bevy
+
UI / Render / WGPU
+
Windows 平台依赖
+
完整 Debug Info
+
Rust Debug 构建产物
```

其中真正能够显著降低体积的方法主要是减少 debug info，但这会直接牺牲项目明确需要保留的调试能力。

Bevy feature 裁剪的实际收益很小。

现有 linking、incremental compilation 等常见开发优化已经存在。

进一步引入 dynamic linking、依赖 O3 或 sccache 都需要牺牲调试体验、磁盘空间或增加额外工程复杂度。

因此 Stage 10 最终采取的原则为：

> 不为了构建产物体积或有限的编译速度收益牺牲完整调试能力，也不为了“必须优化”而引入复杂构建配置。

接受当前 Bevy + Rust full-debug 工程的构建成本。

现阶段实施的有效清理仅包括：

* 删除不再维护的 examples；
* 统一使用 Gallery 作为演示与人工集成验证入口；
* 保留现有 `rust-lld`；
* 保留 Cargo incremental compilation；
* 保留完整 debug info；
* 不额外引入 sccache；
* 不进行收益有限的 Bevy feature 微调。

后续如果 Rust、Cargo 或 Bevy 上游在：

* Debug 构建产物体积；
* incremental compilation；
* linker；
* debug info；
* codegen；
* 动态链接；
* 构建缓存

等方面出现明显改善，再跟随上游重新评估即可。

## 9. Stage 10 状态

Stage 10 可以视为完成。

本 Stage 的主要产出不是强行加入新的构建优化，而是通过测量和实验明确：

> 当前大型构建产物主要属于 Rust + Bevy full-debug 开发环境的结构性成本，而不是 Widgetry 工程设计问题。

因此不再继续针对该问题进行低收益优化。
