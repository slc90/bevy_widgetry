# Bevy 0.19.1 多窗口卡顿调查记录

> 项目：`slc90/bevy_widgetry`  
> 背景：Stage11 自定义 Window / Gallery 多窗口展示  
> 调查环境：Windows，Bevy 0.19.1  
> 日期：2026-09-12

## 1. 问题现象

Stage11 完成自定义 Window 后，在 Gallery 中连续打开多个独立原生窗口时，应用会逐渐出现明显卡顿，最直观的表现是：

- 打开 1 个窗口时基本正常；
- 打开多个窗口后，拖动任意窗口的系统标题栏或自定义标题栏都会明显变得不流畅；
- 窗口越多，卡顿越明显。

最初怀疑点包括：自定义 Window ECS 系统、每窗口 Camera2d、UI 渲染、`start_drag_move()`、resize handles、PresentMode、DX12/Vulkan 后端，以及 winit 本身的多窗口行为。

本次调查的目标是通过逐层剥离，确定卡顿究竟发生在 Widgetry、自定义 Window、Bevy 的窗口集成，还是 Bevy Render / wgpu 多 Surface 路径中。

---

## 2. 最终结论

本次调查得到的核心结论是：

> **卡顿不是 `bevy_widgetry` 自定义 Window 控件造成的，也不是纯 winit 多窗口本身造成的。它可以在“纯 Bevy 0.19.1 + `DefaultPlugins` + 多个原生 `Window`”中独立复现，并且与 Bevy 默认的 `WinitSettings::game()` / `UpdateMode::Continuous` 和多窗口渲染栈组合高度相关。**

将 Gallery 的 App 更新策略改为：

```rust
use bevy::winit::WinitSettings;

App::new()
    .insert_resource(WinitSettings::desktop_app())
    .add_plugins(DefaultPlugins)
    // ...
    .run();
```

后，多窗口拖动恢复流畅。

因此 Gallery 作为桌面 UI / 控件展示程序，应优先使用 `WinitSettings::desktop_app()`，而不是 Bevy 面向游戏场景的默认 `WinitSettings::game()`。

这项设置应属于 **Gallery / App 层策略**，不应放进通用的 `WindowPlugin` 中。

## 3. 调查过程与 A/B 结果

| 实验                                                                                  | 结果     | 说明                                                                       |
| ------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------- |
| 原始 Gallery：多个自定义 Window + Camera2d + UI                                       | 卡       | 初始现象                                                                   |
| 所有窗口改为 `PresentMode::Mailbox`                                                   | 仍卡     | 排除“仅由默认 VSync / FIFO 导致”的解释                                     |
| Gallery 中只创建原生 Bevy `Window`，不创建 Camera、不创建自定义 Window scene          | 仍卡     | 排除 Widgetry Window、UI、Camera、drag/resize 逻辑                         |
| DX12 改为 Vulkan                                                                      | 仍卡     | 排除 DX12 特有问题                                                         |
| 直接使用 `winit 0.30` 创建 6 个窗口                                                   | 流畅     | 排除“winit / Windows 多窗口天然就卡”                                       |
| Bevy 最小窗口程序：`MinimalPlugins + WindowPlugin + WinitPlugin`，不加载 RenderPlugin | 流畅     | 说明 Bevy ECS / bevy_winit 层本身可以流畅                                  |
| Bevy 最小程序：仅 `DefaultPlugins + 6 个原生 Window`                                  | 卡       | 证明问题可脱离 Widgetry 独立复现，并把嫌疑集中到 DefaultPlugins 中的渲染栈 |
| `WinitSettings::continuous()`                                                         | 仍卡     | 默认游戏模式聚焦时本来就是 Continuous，因此没有改善                        |
| `WinitSettings::desktop_app()`                                                        | **流畅** | 找到当前 Gallery 的有效解决方案                                            |

这组结果形成了非常明确的边界：

```text
纯 winit                            -> 流畅
Bevy + winit，无 RenderPlugin       -> 流畅
Bevy + DefaultPlugins + game()     -> 卡
Bevy + DefaultPlugins + desktop_app() -> 流畅
```

## 4. 为什么“纯 Window、没有 Camera”也会卡

一个容易误判的地方是：即使 Bevy `Window` 没有对应 Camera，它也不等于完全与 renderer 无关。

Bevy 0.19.1 的 `WindowRenderPlugin` 会把原生 `Window` 提取到 Render World，并维护每个窗口对应的 `wgpu::Surface`。因此，多窗口并不是只增加几个轻量级 OS 窗口对象，而是增加多个独立的显示 / Surface 出口。

可以把结构粗略理解为：

```text
一个 Bevy App / ECS World
一个 RenderDevice / GPU
        |
        +-- Window A -> wgpu Surface A
        +-- Window B -> wgpu Surface B
        +-- Window C -> wgpu Surface C
        +-- Window D -> wgpu Surface D
```

它并不是“每个窗口启动一个完整游戏进程”，但从渲染出口的角度，比较像“一个游戏同时维护多个独立显示窗口 / swapchain surface”。

Bevy 0.19.1 在没有 Camera 指向某个窗口时，会在初次 present 之后跳过该窗口后续的 swapchain texture 获取，因此本次调查 **没有证明** 卡顿热点一定就在 `get_current_texture()` 或某个具体 wgpu 调用上。

能够确认的是：

1. 只要移除 Bevy Render 栈，多个 Bevy Window 就流畅；
2. 加回 `DefaultPlugins` 后，纯 Window 也会卡；
3. 同样的 `DefaultPlugins` 多窗口程序改成 `desktop_app()` 后恢复流畅。

因此更准确的表述应是：

> **问题来自 Bevy 多窗口渲染栈与 Continuous App 更新模式的组合；具体到 renderer 内部哪个调用占据主要时间，本次没有继续做 profiler 级定位。**

## 5. `game()` 与 `desktop_app()` 的关键区别

Bevy 默认 `WinitSettings::game()` 在应用有焦点时使用：

```rust
UpdateMode::Continuous
```

也就是 App 会持续、尽可能快地执行 update / render loop。对于游戏，这是合理默认值，因为游戏通常需要持续模拟和渲染。

但 Widget Gallery 更接近传统桌面 GUI：大多数时间界面是静止的，只有鼠标、窗口、控件交互或动画发生时才需要更新。

`WinitSettings::desktop_app()` 使用 reactive 策略：

- 窗口事件会唤醒 App；
- 输入事件会唤醒 App；
- `RequestRedraw` 会唤醒 App；
- 到达内部等待超时也会更新；
- 没有事件时，不会像游戏模式那样持续高速跑 render loop。

因此它非常适合 Gallery / Editor / Tooling 这类程序。

可以用下面的方式理解：

```text
game():
    没变化也持续 update -> render -> update -> render -> ...

 desktop_app():
    有事件 / 有重绘需求 -> update / render
    没事                -> 等待
```

当窗口数量增加时，Continuous 模式下多 Surface 相关的固定成本会被每一轮循环持续放大；切换到 reactive 模式后，大量无意义的循环自然消失，因此交互恢复流畅。

## 6. 为什么没有采用 Mailbox 作为解决方案

调查期间尝试过把主窗口和 Demo Window 全部改成：

```rust
present_mode: PresentMode::Mailbox,
```

但实际测试仍然卡顿，因此没有把它作为解决方案。

Bevy 当前有一个相关 issue：

- https://github.com/bevyengine/bevy/issues/25562
- `Bevy slows down to <1FPS when a non-mailbox-vsync window is not "visible"`

该 issue 同样涉及 Bevy 0.19.1、多窗口和渲染节奏，但其环境是 Linux / COSMIC + Vulkan，并且 Mailbox 可以绕过问题。

本项目当前测试表现为：

- Windows；
- DX12 会卡；
- Vulkan 也会卡；
- Mailbox 无效；
- `desktop_app()` 有效。

因此两者可能属于相近的“多窗口 Surface / frame pacing”问题类别，但 **不能认定为同一个具体 bug**。

## 7. 对 Widgetry Window 的结论

本次调查可以排除以下 Stage11 自定义 Window 实现为主要根因：

- `window(...)` BSN scene；
- 每窗口 `UiTargetCamera`；
- 每窗口 `Camera2d`；
- 自定义 TitleBar；
- `start_drag_move()`；
- resize handles；
- Window controls 同步系统；
- maximize/minimize/close 状态同步；
- Widgetry UI 本身。

原因是：在完全不创建这些内容，只保留纯 Bevy `Window` 的最小 `DefaultPlugins` 程序中，卡顿仍然能够复现。

因此没有必要为了这个性能问题去修改 Stage11 Window 控件内部架构。

## 8. Gallery 的正式建议

Gallery 启动时使用：

```rust
use bevy::winit::WinitSettings;

fn main() {
    App::new()
        .insert_resource(WinitSettings::desktop_app())
        .add_plugins(/* Gallery 使用的 plugins */)
        // ...
        .run();
}
```

不要把这项策略放入 `bevy_widgetry_window::WindowPlugin`。

原因是 `WinitSettings` 控制的是整个 App 的事件循环 / 更新模式，而不是单个控件。一个通用 Window 控件库不应该替应用决定它是游戏、编辑器还是桌面工具。

---

## 9. 如果以后某个窗口需要持续动画

Bevy 0.19.1 的 `WinitSettings` 是 **App 级 Resource**，不能给单个 `Window` 设置独立的 `Continuous` / `Reactive` 模式。

同样，`RequestRedraw` 当前也是 App 级消息，会请求应用进行重绘，而不是只唤醒一个指定窗口。

推荐做法仍然是保持：

```rust
WinitSettings::desktop_app()
```

当某段 UI 动画、实时预览或其他内容需要连续刷新时，在动画存续期间发送：

```rust
MessageWriter<RequestRedraw>
```

动画结束后停止发送，App 就自然回到低负载的 reactive 状态。

需要注意：连续发送 `RequestRedraw` 会让整个 App 重新接近 Continuous 行为，因此如果以后出现“只有一个窗口需要长期 60 FPS，而其他多个窗口必须保持极低开销”的需求，可以再进一步做：

- 只让目标窗口对应的动画系统实际更新；
- 控制其他 Camera 的 active 状态；
- 对窗口级渲染策略做更细粒度封装。

当前 Stage11 / Gallery 暂时不需要提前引入这层复杂度。

## 10. 调查中使用过、最终应撤销的临时改动

为了定位问题，曾临时尝试或创建：

- `PresentMode::Mailbox`；
- DX12 -> Vulkan；
- `WinitSettings::continuous()`；
- Gallery 中的“纯 Window”诊断版本；
- 临时 `winit = "0.30"` dependency；
- `winit_multi_window_test.rs`；
- Bevy 最小无 RenderPlugin 多窗口测试 bin。

这些都属于诊断代码，不应成为正式架构的一部分。

最终需要保留的实际策略只有：

```rust
WinitSettings::desktop_app()
```

以及这份调查记录。

---

## 11. 一句话结论

> **Widget Gallery 是桌面 UI 工具，不是需要持续满速运行的游戏；在 Bevy 0.19.1 的多窗口渲染环境下，默认 `game()/Continuous` 会显著放大多 Surface 的成本，而 `desktop_app()/Reactive` 与 Gallery 的实际工作模式匹配，并在本次测试中彻底消除了多窗口拖动卡顿。**
