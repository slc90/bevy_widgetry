# 完成背景能力测试、Gallery 验收与非目标锁定

## 目标

对 Window 图片背景能力做完整收口验证，确认 Theme、Stretch、Cover、opacity、图片延迟加载、resize、borrowed/owned、MessageBox 和 Gallery 行为都符合前述契约，并明确本轮不扩展的边界。

## 范围

本方案负责：

- Window crate 的背景专项测试；
- 现有测试回归；
- Cover helper 与运行时同步验证；
- opacity 验证；
- borrowed / owned 两类入口验证；
- MessageBox 回归；
- Gallery 手工验收；
- 最终能力模型与非目标确认。

## 预期产出

完成后可以确认 Window 图片背景是 `crates/window` 的稳定构造期能力，Gallery 只是展示层；所有新增行为有自动测试或明确手工视觉验收覆盖，没有因为本次功能顺手引入运行时背景系统或通用图片背景抽象。

## 与前后方案的关系

这是拆分链的最后一步。它依赖前四个方案全部完成，用于发现漏迁移、Theme 耦合、Cover 时序、opacity 合成或 Gallery 资源问题；验收完成后本轮方案结束。

## Theme 行为测试

验证 Theme Window：

- root 有 `BackgroundColor`；
- root 有内部 `ThemeWindowBackground` marker；
- root 无用于背景的 `ImageNode`；
- 初始颜色为当前 `theme.window_background`；
- `ThemeChanged` 后背景颜色更新；
- Window border 更新；
- TitleBar border 更新。

还要保留现有 Theme、controls、camera、native window、owned lifecycle 等测试语义。

## Stretch 行为测试

验证 Stretch Window：

- root 有 `ImageNode`；
- root 无 `BackgroundColor`；
- `ImageNode.image` 为调用方传入 handle；
- `image_mode == NodeImageMode::Stretch`；
- `rect == None`；
- opacity 正确写入 ImageNode 的 alpha；
- `ThemeChanged` 不替换 image、不修改 mode、不修改 opacity；
- Window border 和 TitleBar border 仍正常响应 Theme。

图片 mode 与 Theme border 的职责必须能同时成立，不能因为 Image Window 没有 BackgroundColor 就漏掉 border 更新。

## opacity 测试

分别至少验证：

```text
opacity = 1.0
opacity = 0.5
opacity = 0.0
```

确认它只改变图片整体 alpha，不改变 RGB，不创建 Theme 背景层，也不改变 `Stretch` / `Cover` 的几何与 crop 语义。

本轮构造契约使用 `0.0..=1.0` 的 opacity；测试重点是合法区间内语义，不扩展运行时 setter。

## Cover 裁剪 helper

至少覆盖：

```text
原图更宽
原图更高
宽高比完全相同
```

断言计算出的 rect：

- 位于原图范围内；
- 保持目标 node 宽高比；
- 从中心裁剪；
- 一条轴完整保留；
- 另一条轴对称裁剪。

使用前面 `1000×800 → 1920×1080` 的场景可以作为可读性示例，预期取原图中央 `1000×562.5` 区域，上下对称裁剪。

## 零尺寸保护

覆盖：

```text
node width = 0
node height = 0
image width = 0
image height = 0
```

这些输入不应 panic，不应生成 NaN / Infinity，也不要求产生新的有效 crop rect。

当后续 node 恢复到有效尺寸时，系统仍能重新计算正常 rect。

## 图片延迟加载

验证 Image/Cover Window 在 asset 尚未存在时：

```text
无 BackgroundColor
→ 背景语义为透明
→ 不 panic
→ 不切换到 Theme
```

随后向 `Assets<Image>` 提供对应图片：

```text
→ 获取并缓存固有尺寸
→ 根据当前 ComputedNode.size 生成正确 rect
```

这个测试覆盖“构造时 handle 已有，但图片晚到”的正常异步 asset 场景。

## Cover resize

图片加载完成后改变 WindowRoot 的最终布局尺寸，验证：

```text
ComputedNode 发生变化
→ rect 按新的 node aspect ratio 更新
```

同时确认：

- image handle 不需要替换；
- ImageNode 不需要重新创建；
- 不依赖 native WindowResized event；
- 不需要手动维护 `last_node_size`；
- opacity 在 resize 前后保持不变。

## 图片尺寸验收边界

不要求用超大图片做性能 Demo。

Window crate 不限制图片大小、不自动 downscale。Gallery 使用已经预处理到合理尺寸的 asset。

如果调用方未来传入极大纹理，主要风险属于 texture 内存与 GPU 设备限制，而不是 Cover resize 计算；这不改变本轮验收标准。

## 最终能力模型

完成后背景模型应保持：

```text
WidgetryWindowBackground

├── Theme
│   ├── theme.window_background
│   └── 响应 ThemeChanged
│
└── Image
    ├── image: Handle<Image>
    ├── opacity: 0.0..=1.0（构造期）
    ├── 图片未加载 → 背景透明
    ├── image / mode / opacity 不响应 ThemeChanged
    │
    ├── Stretch
    │   └── 填满 WindowRoot，允许变形
    │
    └── Cover
        ├── 保持宽高比
        ├── 中心裁剪
        ├── 始终填满 WindowRoot
        └── resize 后根据最终 ComputedNode.size 更新 rect

Window border / TitleBar border
└── 两种背景模式下都继续响应 Theme
```

这项能力属于 `crates/window` 本身，Gallery 只负责消费和展示。
