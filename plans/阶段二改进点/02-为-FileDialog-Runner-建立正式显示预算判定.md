# 为 FileDialog Runner 建立正式显示预算判定

## 目标与范围

在 `gallery/benches/file_dialog_run.py` 增加明确的正式验收模式，并同步 `file_dialog.py` 的结果读取契约和 `file_dialog.md`。保留现有采集器、显示关联适配器和原始数据，不改动 FileDialog 业务代码。

## 现状与修改设计

分析器已经依据全部有效显示样本的 `input_to_presented_upper_ms <= 150` 生成 `150ms_target_passed`。证据完整时为 true 或 false，显示证据不足时为 null。Runner 目前只保存 `report.json`、把 samples 放进汇总，然后输出采集完成；这不等于预算通过。

增加显式启用的严格显示预算验收选项。每次运行的汇总分别保留采集是否完成、实际显示证据是否完整、预算是否通过。只有预期运行和样本全部完成、显示关联有效、预算结论全部为 true，才能给出正式通过。任何 false 都保留预算未通过事实；任何 null 都保留验收未完成事实。混合结果应同时显示失败项和缺证据项，而不是用一个含糊的布尔值抹平差异。

严格模式对预算失败、证据不足和采集或报告错误返回可区分的非成功结论，并在文档中固定机器可读状态与退出状态的含义。纯采集默认流程仍可在成功采集后正常结束，但输出必须明确不是正式性能通过。`--control` 只用于测量探针开销，不允许被解释为显示预算验收；与严格验收选项冲突时明确拒绝配置。

保持当前输入时间边界、精确的内容帧关联、Root／Session／Native Window／Camera 身份匹配和映射不确定度。不能跳过慢样本、只挑后续热样本、把 CPU submission 当作实际显示，或用 BRP 往返与 Screenshot 耗时代替显示时间。DirectComposition 等环境缺少可靠关联时，结论只能是不完整。既有 Worker、窗口、Camera、Session 和资源回收检查继续独立生效。

## 实施约束

涉及编译和运行的验证使用现有 Bevy 0.20、Windows 64 位 MSVC／DX12 环境，不以跨平台适配或绕过目标限制代替验证。

## 完成条件

用小型确定性报告 Fixture 覆盖全 true、含 false、含 null、混合失败与缺证据、空样本、预期数量不足、损坏报告以及 control／严格模式冲突。覆盖恰好 150 ms 与不确定度使上界越过 150 ms 的边界，不能通过重新计算更宽松指标绕开分析器。

正式 Windows 测量保留每个独立进程的 Trace、报告、运行配置和原始显示证据；采集完成、资源正确性与预算结论分别可查。未获得实际显示证据的环境不能宣称通过，但仍能使用纯采集流程定位问题。

## 预期产出

可供人工和自动化明确判断通过、失败与未完成的 Runner 接口、汇总格式和相应回归验证。
