# Stage4 总结：现有控件架构调研与重构

## 1. Stage4 的定位

Stage4 的目标不是新增控件，而是对 Stage1～Stage3 已经形成的 Button / ComboBox 代码进行一次架构复盘和重构。

本阶段主要完成三件事：

1. 调研 Bevy 0.19.1 官方 UI / headless widget 的设计方式；
2. 判断现有代码中哪些逻辑值得抽取、哪些不应该抽象；
3. 整理测试基础设施和视觉回归测试架构。

Stage4 的核心原则始终是：

> **重复代码不等于重复抽象。**

以及：

> **只抽取独立、稳定、重复的逻辑动作，不为了“看起来统一”而制造框架。**

---

# 2. 对 Bevy 0.19.1 官方架构的结论

本阶段重点阅读和分析了 Bevy v0.19.1 中：

- `bevy_ui`
- `bevy_ui_widgets`
- Button
- Checkbox
- RadioButton / RadioGroup
- ListBox / ListItem
- Slider
- Menu
- Feathers theme 相关实现

最终形成的认识是：

```text
bevy_ui
├─ Pressed
├─ InteractionDisabled
├─ Checked / Checkable
├─ Selected / Selectable
└─ 通用 UI 状态

bevy_ui_widgets
├─ Activate
├─ ValueChange<T>
├─ Button
├─ Checkbox
├─ RadioButton / RadioGroup
├─ ListBox / ListItem
├─ Slider
└─ Menu
```

官方并没有设计一个统一的：

```text
Widget trait
SelectionModel<T>
Pressable trait
Universal Style Resolver
Two-way Binding Framework
```

而是优先复用稳定的 UI 语义组件和事件。

例如：

```rust
Activate
ValueChange<T>
Pressed
InteractionDisabled
Selected
```

控件本身则根据自己的语义进行组合。

因此 Widgetry 后续继续遵循：

> **复用 Bevy 已经稳定的 UI 语义，而不是再造一层通用 Widget 框架。**

---

# 3. Headless 层结论

## 3.1 LongPressButton

LongPressButton 继续定位为：

> 对官方 headless Button 的能力扩展。

结构保持：

```rust
#[require(Button)]
pub struct LongPressButton {
    pub press_duration: u64,
}
```

不重新实现自己的 Button。

Widgetry 只增加：

```text
Press
↓
建立 LongPressPending
↓
计时
↓
LongPressEvent
```

同时：

```text
Release / Cancel / DragEnd
↓
取消 LongPressPending
```

官方 Button 自身负责的：

```text
Pressed
Activate
pointer press/release lifecycle
```

不再由 Widgetry 重复测试。

---

## 3.2 ComboBox

ComboBox 的核心结构继续使用固定 Hierarchy：

```text
ComboBox
├─ Field
└─ Popup
   └─ Option...
```

组合官方：

```text
Button
ListBox
ListItem
Selected
ValueChange<T>
```

而不是建立新的通用 selection framework。

---

# 4. ComboBox Hierarchy 重构

Stage4 将 ComboBox 内部重复出现的 Hierarchy 查询知识集中起来。

最终采用了 ComboBox 本地的 `SystemParam`：

```rust
ComboBoxHierarchy
```

它负责查询：

```text
root → field
root → popup
option → root
```

这一设计满足几个重要原则：

```text
Hierarchy 仍然是真实来源
不缓存内部 Entity
不引入 ComboBoxParts
不做通用 ECS hierarchy framework
只表达 ComboBox 自己的固定结构
```

因此没有采用：

```rust
struct ComboBoxParts {
    field: Entity,
    popup: Entity,
}
```

也没有引入：

```rust
find_descendant_with<T>()
```

这类通用 production helper。

---

# 5. ComboBox selection 重构

用户选择和程序化选择中重复的核心逻辑是：

> 将某个 Option 变成当前唯一的 `Selected`。

Stage4 把这一部分抽成：

```rust
set_selected_option(...)
```

但没有合并两条事件链。

## 用户选择

```text
ListBox ValueChange<Entity>
↓
验证 source / option
↓
更新 Selected
↓
关闭 Popup
↓
对外发送 ValueChange<usize>
```

## 程序化选择

```text
SetComboBoxSelected
↓
验证 index
↓
更新 Selected
```

继续保持：

- disabled 状态下程序化选择仍然有效；
- invalid index 不破坏旧 selection；
- 程序化选择不发送 `ValueChange<usize>`；
- 程序化选择不伪造 `ValueChange<Entity>`；
- 程序化选择不会额外关闭 Popup。

形成了本阶段另一个重要原则：

> **复用状态变换，不复用事件链。**

---

# 6. ComboBox Styled 层重构

## 6.1 Resolver 保持控件本地

现有：

```rust
resolve_combo_box_field_style(...)
resolve_combo_box_option_style(...)
```

继续保留。

状态优先级属于控件语义，因此不建立通用：

```text
StyleResolver
Priority System
State Machine Framework
```

Field 当前优先级仍然是：

```text
Disabled
↓
Open
↓
Pressed
↓
Hovered
↓
Default
```

Option 当前优先级仍然是：

```text
Disabled
↓
Hovered
↓
Selected
↓
Default
```

---

## 6.2 Refresh 逻辑集中

Stage4 将重复的 style recalculation 收敛到：

```text
FieldStyles::refresh
OptionStyles::refresh
```

结构变成：

```text
Changed / Added / RemovedComponents system
                ↓
        决定“什么时候刷新”
                ↓
          refresh(...)
                ↓
       读取当前 ECS 状态
                ↓
          resolver(...)
                ↓
       应用完整 style
```

也就是说：

> system 管触发时机，refresh 管完整重算，resolver 管状态优先级。

这个结构被认为适合继续保留。

---

# 7. `setup_styled_combo_box`

Stage4 没有为了追求“函数复用率”强行让 setup 调用所有 runtime refresh helper。

原因是：

```text
setup
```

主要负责一次性构造：

- Root layout；
- Field visual；
- Field text；
- dropdown icon；
- Popup visual；
- Option visual；
- Option text。

这些操作与 runtime mutable refresh 的职责不同。

因此本阶段确认：

> **函数大，不代表一定要继续拆；结构职责不同，也不需要强行复用。**

---

# 8. Field Text 同步

Field 显示文本继续从真正的：

```rust
Selected
```

状态派生。

没有改成监听：

```rust
ValueChange<usize>
```

因为 `Selected` 才是当前状态的 source of truth。

因此：

```text
Selected changed
↓
Option → Root
↓
Root → Field
↓
更新 Field Text
```

程序化 selection 和用户 selection 都能自然走同一条显示同步路径。

---

# 9. 新增 workspace `test_utils`

Stage4 新增：

```text
crates/test_utils
```

crate：

```text
bevy_widgetry_test_utils
```

用途仅为测试。

其他 crate 通过：

```toml
[dev-dependencies]
```

使用。

同时设置：

```toml
publish = false
```

明确它不是正式发布 API。

---

## 9.1 当前 `test_utils` 只负责 Pointer 测试输入

统一了：

```text
primary_press
primary_release
primary_click
primary_cancel
primary_drag_end
```

以及：

```text
press
release
cancel
drag_end
```

等便捷调用。

这样 Button / ComboBox 的 unit test 和 integration test 不再各自重复构造：

```rust
Pointer::new(...)
Location { ... }
HitData { ... }
```

---

## 9.2 没有提前塞进 `test_utils` 的内容

当前明确不放：

```text
ComboBox hierarchy helper
ComboBox fixture
style assertion
visual renderer
baseline compare
控件专用 test common
```

因为这些还不是稳定的跨控件测试基础设施。

# 10. LongPress 测试整理

Stage4 删除了只是在证明官方 Button 行为的测试。

LongPress 当前测试重点回到 Widgetry 自己拥有的语义：

```text
Press → 开始 long press
Release → 取消
Cancel → 取消
DragEnd → 取消
threshold → LongPressEvent
Disabled → 不响应
自定义 duration → 正确
```

内部 unit test 只保留少量有诊断价值的：

```text
Press 会建立 LongPressPending
自定义 duration 会进入 Timer
```

避免 integration test 和 implementation-detail test 大面积重复。

---

# 11. ForegroundColor 测试职责归位

原本 StyledButton tests 中存在几条实际上是在测试：

```text
ForegroundColorPlugin
```

本身的行为。

Stage4 将它们迁移到：

```text
crates/core/tests/foreground_color.rs
```

由 core 自己测试：

```text
ForegroundColor hierarchy propagation
ForegroundColor → TextColor
ForegroundColor change → TextColor change
```

Button 只保留：

> StyledButton 是否正确设置自身的 foreground 状态。

同时，本阶段没有重新设计 ForegroundColor。

明确没有做：

```text
ThemeToken
UiTheme
Feathers Theme 架构迁移
ForegroundColor 最终设计
```

这些留到后面的工程化阶段讨论。

---

# 12. 视觉回归测试重构

Stage4 最大的测试架构变化是 visual regression。

原先多个完整 Bevy renderer App 位于同一个 integration-test executable 中。

这会遇到 Bevy `DefaultPlugins` 中的 process-global 初始化问题，例如：

```text
LogPlugin
TaskPool
其他未来可能增加的全局状态
```

因此 Stage4 将视觉测试拆成：

```text
tests/
├─ visual_button.rs
└─ visual_combo_box.rs
```

Cargo 会把它们编译成两个独立 test executable。

最终原则：

```text
一个 visual_*.rs
↓
一个 test process
↓
一个完整 Bevy renderer App
```

如果未来需要另一套独立视觉场景：

> 新建新的 `visual_*.rs` target，而不是在同一个 test binary 中再初始化一套完整 Renderer App。

这个约束已经写入 visual test support 的注释中。

---

# 13. Visual common infrastructure

视觉测试重复的 renderer / readback / baseline compare 流程已经集中到：

```text
tests/common/visual.rs
```

大致负责：

```text
setup_offscreen_app
create_render_target
readback_image
assert_matches_baseline
```

避免 Button / ComboBox 各自维护一套完整 offscreen renderer。

没有建立大型：

```text
VisualTestBuilder
VisualFramework
```

继续保持简单 helper 结构。

---

# 14. Visual Scene 单一来源

Button / ComboBox 的视觉场景现在统一放在：

```text
tests/common/scenes/
├─ button.rs
└─ combo_box.rs
```

Button scene：

```text
Default
Hovered
Pressed
Disabled
```

ComboBox scene：

```text
Default
Open + hovered option
Disabled
```

Scene 只负责：

> **画什么。**

Visual infrastructure 负责：

> **怎么渲染。**

Regression test 负责：

> **和哪个 baseline 比。**

---

# 15. Baseline Generator 分离

Baseline generator 不再属于：

```text
cargo test
```

而是独立 manual example：

```text
examples/generate_baseline.rs
```

使用方式类似：

```bash
cargo run -p bevy_widgetry --example generate_baseline -- button
cargo run -p bevy_widgetry --example generate_baseline -- combo_box
```

generator 和 regression test 共用同一套：

```text
tests/common/scenes
tests/common/visual
```

因此不会再出现：

```text
generator scene
≠
regression scene
```

的漂移风险。

---

## 15.1 Module 组织

visual integration tests 使用标准 Rust module tree：

```rust
mod common;

use common::{
    scenes::button as scene,
    visual,
};
```

generator 因为是独立 example target，则保留必要的：

```rust
#[path = "../tests/common/mod.rs"]
mod common;
```

这里的 `#[path]` 是有实际原因的跨 target 源码复用。

---

# 16. Baseline 原则

Stage4 是重构，不是视觉调整。

因此：

```text
tests/baselines/*.png
```

不应该为了“让测试通过”而重新生成。

如果视觉结果发生变化，应优先判断：

> 是否重构意外改变了行为或样式。

而不是直接覆盖金标准。

---

# 17. Public API 测试

`public_api.rs` 继续显式验证 facade re-export。

这里的机械重复是测试目的本身，因此没有抽 macro 或泛型 helper。

原则：

> **测试“明确列出公开 API”时，重复本身就是可读性。**

# 19. 本阶段形成的几条长期判断

## 19.1 重复代码不等于重复抽象

官方 Bevy 自己也存在 Button / Checkbox / RadioButton 中相似的 Pressed lifecycle 代码。

这说明：

> 如果语义并没有稳定统一，仅仅代码长得像，不足以建立抽象。

---

## 19.2 复用状态变换，不复用事件链

ComboBox selection 是本阶段最典型的例子。

```text
用户事件
程序化命令
```

可以共享：

```text
“更新唯一 Selected”
```

但不能共享：

```text
关闭 Popup
外发 ValueChange
用户交互语义
```

---

## 19.3 状态优先级属于控件语义

例如：

```text
ComboBox Field:
Disabled > Open > Pressed > Hovered > Default
```

这不是一个适合全局抽象的排序规则。

每个控件应该保留自己的 resolver。

---

## 19.4 Hierarchy 可以抽，但只能抽控件自己的结构知识

允许：

```text
ComboBox root → field
ComboBox root → popup
ComboBox option → root
```

不意味着应该做：

```text
通用 descendant finder framework
```

---

# 20. 对后续工程化阶段的观察

Stage4 之后已经越来越明显：

Widgetry 后续真正需要重点工程化的，很可能不是更多“跨控件代码抽象”，而是：

```text
控件开发流程
目录组织
命名约定
测试要求
visual regression 要求
public API 检查
文档结构
发布结构
```

也就是：

> **工程流程上的统一，可能比生产代码上的统一更重要。**

但这一点只作为阶段性观察保留。

第一批 Stage 完成后，再专门讨论：

```text
Theme
ForegroundColor
crate / feature
public API
WidgetryPlugins
控件开发 Convention
测试规范
目录规范
```

# 22. Stage4 完成后的下一步

Stage4 结束后，项目可以继续进入后续功能 Stage。

当前整体规划仍然是：

```text
Stage1～Stage3
→ 已有控件功能建立

Stage4
→ 官方架构调研 + 现有代码重构

后续 Stage
→ 继续实现计划中的控件 / 能力

第一批 Stage 完成后
→ 再进入完整工程化重构阶段
```

其中之前已经确定：

- TextField 阶段不重新实现自己的 Headless TextField，而是扩展官方 headless / EditableText 能力；
- Stage8 之前增加 SVG 图标支持阶段；
- Stage8 以后继续扩充控件，具体控件到时再决定。
