# 补齐 ScrollArea 按钮的业务操作日志

## 目标与设计思路

ScrollArea 页拥有两个具有明确应用语义的示例按钮，但其处理器目前没有 INFO。本增量只补齐这些按钮引发的离散业务事实，不记录一般滚轮、Scrollbar 或自动滚动的中间过程，也不修改 Widgetry ScrollArea 的行为。

## 两个独立动作在同一演示区域中的记录

`gallery/src/pages/scroll_area.rs` 的 `toggle_auto_content()` 在 `On<Activate>` 进入后将示例内容高度从 `80px` 切换为 `290px` 或反向切换。这个行为同步完成，可以在实际设置新高度后记录一次 INFO，附上应用侧已知的目标与新高度；如果目标无效或者没有任何内容被更新，就不能写成成功。若用户确实发起了动作但未产生状态变化，记录这次未变化的结果，而不是静默跳过。实际普通 Layout 重算不产生 DEBUG。

`trigger_scroll_into_view()` 收到另一个 `On<Activate>` 后，通过 `commands.trigger(WidgetryScrollIntoView { entity: target })` 发出请求。应用层应在该请求确实提交时记录一次 INFO，表明“用户请求将目标滚动到可见区域”，包括 `target`。这一提交不保证经过布局、裁剪等步骤后目标已经出现在视口，不能虚构“滚动完成”；没有可用目标时应记录符合实际的未提交结果，而不是成功。

两条日志直接放在各自现有应用操作处理路径，不新建轮询 System，不在通用控件库里记录 Pointer 点击。普通滚轮拖动、滚动位置逐帧同步和自动尺寸调整继续静默；只有明确的应用动作才写 INFO。

新增日志正文统一中文，动态上下文使用英文结构化字段；只记录必要的对象身份、状态和结果摘要，不打印完整用户输入、敏感内容或大体量业务数据，也不手动重复 Tracing 已提供的 `file`、`line`、`module_path`、`crate_name` 等元数据。

## 验证与边界

验证切换两种内容高度、重复触发、缺少目标 Entity、ScrollIntoView 消息提交等场景：单次离散动作得到单条语义 INFO，且“已请求”不会被测试误认成“实际完成滚动”。日志消息用中文、动态字段英文，不记录输入事件轨迹。已有 UI 状态、布局机制、事件路由和错误传播不应改变。

`docs/gallery.md` 同步相应示例的已实现可观察行为。这个目标与 Slider 的拖动结尾没有技术依赖，尽管在实施序列上相邻，仍独立验收。
