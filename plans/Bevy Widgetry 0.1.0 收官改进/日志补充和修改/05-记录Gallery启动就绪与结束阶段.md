# 记录 Gallery 启动就绪与结束阶段

## 目标与设计思路

让 Gallery 的运行日志能够回答“进程启动到了哪一步、界面何时真正可用、应用主循环何时返回”这三个问题。全部属于程序自身的实际生命周期，使用 DEBUG，不为正常启动增加 INFO。与单独的退出交互／托盘收尾增量不同，此处只关注应用入口、启动就绪和进程最终返回。

## 现有边界及记录时机

`gallery/src/main.rs` 的 `main -> run` 已负责准备日志文件、注册宿主 Error Handler、安装 Bevy `LogPlugin`、构造插件并运行 `app.run()`；完成后通过 `LoggingGuard::finish()` 等待刷盘并确定退出码。但运行阶段尚没有统一的普通 DEBUG 事件。日志在 Subscriber 尚未安装前无法可靠进入正式文件，因此不能虚构“进程最初启动”已成功落盘。

在日志完成安装并可输出之后记录“Gallery 启动配置开始”之类的首个真实阶段；完成插件／必要资源装配且准备进入 `app.run()` 时记录“应用已开始运行”，注意这不等于窗口完成第一帧或可交互。

就绪标志应依据现有 `GalleryFirstFrameReady`、`SplashLifecycle` 和页面初始化状态确定。`gallery/src/splash/lifecycle.rs` 已有 Assets 等待、Splash 播放、淡出结束和 `GalleryPage::Button` 等约束；正常启动不能仅在 `setup()` 排队 `NextState::Button` 后就写“Gallery 已就绪”。建议让掌握真实就绪事实的阶段在状态转换时发出一次 DEBUG：Splash 完成交接时为真正可见的首帧；Splash 禁用或基准测试等特殊启动路径则使用它们既有的就绪节点，不能因缺少 Splash 而永远没有成功就绪记录。

主循环返回后记录实际 `AppExit` 结果，并确保在执行 `guard.finish()` 之前发出该记录。`finish()` 失败本身沿用独立应急错误诊断和失败退出码，不用伪造一条“日志已全部持久化”的 DEBUG；应用发生启动失败或其他 ERROR 时，保留 `diagnostics::startup` 的原始错误诊断机制。

`gallery/src/config.rs` 在配置文件不存在、使用内存默认值并尝试创建文件时，目前用 INFO 描述正常初始化分支；它不是用户业务操作，应根据真实诊断价值降为 DEBUG 或保持静默。实际读取、解析、校验、保存失败仍保留现有源头 ERROR 和实际处理 DEBUG，不以 WARN 或一条正常启动 DEBUG 取代。

## 重要状态的语义

`Splash` 资源加载等待、逐帧动画及轮询状态不记录。只有真实跨越有意义的阶段（例如可播放、交接、完成）才适合 DEBUG，不能把 `SplashPhase` 每一帧的判断都写出来。用户点击 Skip 的 INFO 已在 `gallery/src/splash/skip.rs`，继续保留；自动播放完成只产出程序运行 DEBUG。资产加载失败、节点缺失和等待超时仍按现有异常／错误约定处理，不因增加运行日志重新定义错误处理策略。

不引入新的周期性 `Update` 监视器；优先挂在已有的状态提交、完成事件或一次性生命周期函数中。若单个阶段会因屏幕重绘／重入检查多次触达，必须以现有状态转换的一次性事实为准，不增加重复回报。

新增日志正文统一中文，动态上下文使用英文结构化字段；只记录必要的对象身份、状态和结果摘要，不打印完整用户输入、敏感内容或大体量业务数据，也不手动重复 Tracing 已提供的 `file`、`line`、`module_path`、`crate_name` 等元数据。

## 验证与文档

验证正常有 Splash 和禁用 Splash 两种启动路径、实际已交接的第一帧、启动失败路径、正常退出与错误退出码。重点检查各 DEBUG 的真实顺序：“已进入主循环”不会先于插件装配，“已就绪”不会先于实际首帧／交接，“进程退出结果”会在日志 Guard 结束前产生。运行时可以使用既有 Gallery 启动探针与 BRP 能力，不必额外创建测试用 GUI 模型；涉及可观察窗口行为时在 Windows 环境进行专项验证。

在 `docs/gallery.md` 的启动与 Splash 段落补充已经实现的正常 DEBUG 阶段，不能将“请求就绪”和“实际就绪”混称。用户操作与页面转换日志留给对应增量，避免在应用入口重复记录导航动作。
