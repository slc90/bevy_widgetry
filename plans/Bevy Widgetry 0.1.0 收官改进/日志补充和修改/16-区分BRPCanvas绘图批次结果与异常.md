# 区分 BRP Canvas 绘图批次结果与异常

## 目标与设计思路

让 BRP Canvas 批量修改保持“一个业务批次及其结果”的清晰 INFO，同时不把每个预期的输入拒绝错误都当成 WARN，也不将真正的内部失败降为一般业务拒绝。这个增量只涉及绘图批次及其回报，不改变任何几何操作、批次执行顺序或持久化协议。

## 现有记录点与问题

`gallery/src/canvas_experiment/drawing.rs::batch` 一次接受最多 1024 个操作，逐项使用 `serde_json::from_value::<Operation>()` 和 `apply(...)`，返回每项 `index`、`ok`、成功 ID 或失败对象；单项失败不会中断剩余操作。目前每项失败都记录 `warn!(session, index, error, "BRP 绘图操作失败，保留此前成功修改并继续批次")`，结束时记录 `info!(session, successful, total, "通过 BRP 完成绘图批次")`。

这里有两个区别必须清楚：用户发送一项无效参数而得到预期的拒绝，不自动意味着环境异常或资源风险；反之某个内部操作确实出错，即使批次继续执行，已发生的真实错误也不能只以 WARN 表达。错误是否已有源头 ERROR，要根据 `BrpError` 的产生路径及现有领域诊断判断，不通过日志文案猜测。

## 记录批次意图和结果

BRP 批次是一个明确的语义操作。对合法发起的批次，在接受和执行结束时以 INFO 描述实际业务结果，包含 `session`、`origin = "brp"`、`total`、`successful`、`failed`、`all_succeeded`，以及 `persistence.saved`／必要的保存失败摘要。若请求一开始就因参数或操作数上限被拒绝，不得记录“批次已执行成功”，应在已识别的应用入口记录实际拒绝结果。

单项失败仍逐一写入原有 BRP `results` 并保留原错误详情，日志不用替代结构化响应，也不完整复制最多 1024 项的原始输入。对于可预期的单项业务拒绝，不再无条件记录 WARN；在批次 INFO 的失败数量和返回结果中体现即可。只有尚未构成 ERROR 却存在真正异常或风险时才使用 WARN；如果 `apply` 内部发生真实错误，保留其已有源头 ERROR 和处理 DEBUG，绝不能用删 WARN 的方式删除错误诊断。

批次运行中的成功修改、后续失败与持久化失败本来就可能同时出现。日志应忠实表示“部分成功”“写盘失败”等实际结果，不因 `batch` 返回 `Ok` 就在 INFO 中声称所有项都成功。普通逐项遍历、数据结构内部更新及不具有独立应用业务语义的循环步骤不写 DEBUG／INFO，避免大批量修改制造日志风暴。

新增日志正文统一中文，动态上下文使用英文结构化字段；只记录必要的对象身份、状态和结果摘要，不打印完整用户输入、敏感内容或大体量业务数据，也不手动重复 Tracing 已提供的 `file`、`line`、`module_path`、`crate_name` 等元数据。

## 验证与边界

用现有 BRP 批次用例验证全部成功、部分无效参数、混合业务拒绝与真实内部失败、空批次、超出 1024 项限制，以及批次修改成功但持久化失败。确保返回 `results`、`successful`、`all_succeeded` 和 `persistence` 与操作真实状态不变；日志 INFO 摘要字段与返回值一致；预期业务拒绝不会刷 WARN；真正 ERROR 的首次源头及已有处理链不丢失。普通只读查询不因此增加日志。

同步 `docs/gallery.md` 中批次结果与保存状态的日志说明。此增量与阶段导出只共享相同 Document／存档基础设施，不需要更改 Stage 的流程或状态语义。
