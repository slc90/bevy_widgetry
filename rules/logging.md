# 日志规则

## 一、职责与统一入口

日志由掌握事件语义的模块负责记录。底层通用组件不得推测上层业务含义，也不得将日志作为事件、状态或错误传播机制的替代品。

Widgetry 库负责自身的诊断日志，包括日志等级、消息内容和必要的结构化上下文。日志订阅、过滤、格式、输出目标及持久化由宿主 App 负责。Widgetry 库不得自行配置宿主日志系统。

`bevy_widgetry_app_logging` 是供宿主选择使用的日志配置能力，不受 Widgetry 内部日志 Macro 和 Plugin 注册日志要求约束。

Widgetry 库统一使用内部日志 Crate 提供的 Macro：

- `widgetry_trace!`
- `widgetry_debug!`
- `widgetry_info!`
- `widgetry_warn!`
- `widgetry_error!`

统一使用 `target: "bevy_widgetry"`。库代码不得直接使用 Bevy 日志 Macro 绕过统一入口。

Gallery 和其他业务程序使用各自的日志入口，不使用 Widgetry 内部日志 Macro，也不固定 Widgetry 的日志 Target。

错误的构造、传播、处理、错误 ID 及 ECS 兜底遵循 `rules/code.md`，本文只规定日志行为。

## 二、日志等级

日志等级根据事件性质确定，不单纯根据事件是否重要判断。

### ERROR：真实错误

用于记录已经实际发生的错误。

真实错误首次发生时必须记录 ERROR，即使后续能够恢复、重试或降级处理，也不得因此降低等级。

ERROR 应提供错误 ID、失败原因及必要的上下文，不得以记录日志代替错误处理或传播。

同一错误在传播过程中不得重复记录相同的失败原因。错误处理与 ECS 兜底日志遵循 `rules/code.md`。

### WARN：异常与风险

用于尚未构成真实错误，但存在明确异常、风险或功能受限的情况。

包括环境条件异常、资源压力以及可选能力受限等情形。

WARN 不用于正常等待、正常取消、普通状态变化，也不得用于代替可以恢复的 ERROR。

### INFO：业务操作与结果

用于记录具有明确业务语义的操作及其结果，主要由 Gallery 或业务程序产生。

用户明确发起的语义操作均应记录，不以操作是否重要、是否改变状态作为记录门槛。

具有独立业务意义的程序自动操作及其结果也可以记录 INFO，并应在必要时区分触发来源。

INFO 记录业务含义，不记录底层输入机制。通用 UI 控件不因收到 Pointer 或 Keyboard 事件而产生业务 INFO。

Widgetry 库原则上不记录用户操作；仅在确有必要时记录库自身的重要事件，不要求为了使用 INFO 而增加日志。

### DEBUG：程序运行与执行过程

用于记录具有诊断价值的程序生命周期、内部执行阶段、状态转换及真实错误的处理情况。

主要包括：

- 程序启动、就绪、退出等生命周期节点。
- 页面或应用状态的实际切换。
- 与业务流程相关的线程和异步任务的启动、完成、取消及结束。
- 真实错误首次被处理时的处理结果和措施。
- Widgetry Plugin 注册完成及必要的库内部生命周期节点。

DEBUG 不要求记录每次函数调用、ECS System 执行或内部状态同步。

### TRACE：临时开发诊断

TRACE 仅用于开发期间的细粒度或高频诊断，例如逐帧更新、频繁事件和中间状态。

只有确有诊断价值时才允许增加 TRACE，不得为了记录而记录。

开发任务完成后，必须移除临时 TRACE 调用。正式提交的库和应用实现代码不得保留 TRACE 调用，包括通过条件编译隐藏的调用。

允许保留 `widgetry_trace!` 的宏定义。使用现有 Clippy `disallowed_macros` 机制检查遗留调用，不开发独立的自定义 Lint。

## 三、操作与执行生命周期

### 业务操作

业务操作日志应描述用户或程序要求执行什么，以及实际取得了什么结果。

对于立即完成的同步操作，可以在结果确定时记录一次。

对于异步、延迟或分阶段操作，应区分操作发起与最终结果，不得在结果尚未确定时提前记录成功。

用户明确发起操作，即使最终没有改变状态，也应记录操作及其未变化的结果。

程序内部常规同步、重复设置和无业务意义的 No-op 不因此产生业务日志。

### 程序执行

程序内部执行过程使用 DEBUG，和业务操作 INFO 可以同时存在。

例如用户切换页面时，业务程序记录用户选择页面的 INFO，负责页面状态的模块记录实际切换结果的 DEBUG。

程序自动触发的页面切换不需要虚构用户操作日志。

### 线程与异步任务

只要求记录项目自身管理、与业务流程相关且具有明确生命周期的线程与异步任务。

应根据实际执行情况记录启动、完成、取消请求、实际取消和结束等有诊断价值的节点。

取消请求不等于取消完成，退出请求也不等于线程已经结束。

不得强制追踪 Bevy 内部任务调度、任务轮询或大量短期并行计算。

如果用户操作触发了异步任务，业务操作使用 INFO，任务内部生命周期使用 DEBUG。两者应能够关联，但不得重复表达同一事实。

## 四、日志关联与内容

日志正文统一使用中文，动态信息采用英文命名的结构化字段，例如：

`error_id`、`operation_id`、`task_id`、`entity`、`path`、`action`、`error`。

正文说明发生了什么，结构化字段提供必要的诊断上下文。

同一次多阶段操作需要关联时，应使用一致的 `operation_id` 或其他合适标识；同一错误使用一致的 `error_id`。

字段应足以识别操作、目标、关键参数及实际结果，但不要求所有日志具备相同的固定字段。

不得为日志完整记录用户输入、敏感数据或无必要的大型数据内容。

不手动添加 `file`、`line`、`module_path`、`crate_name` 等已有 Tracing Metadata，由宿主决定显示方式。

## 五、重复记录与持续异常

同一日志不应重复描述已经记录且没有新增诊断价值的事实。

对于持续存在的同一异常状态：

- 正常进入异常时记录一次相应等级的日志。
- 异常持续期间不因重复检查而反复记录。
- 异常实际恢复时记录一次 DEBUG。
- 恢复后再次进入异常状态时重新记录。

持续状态去重不得抑制新产生的独立错误。

正常等待不代表异常已经恢复，Entity 销毁也不自动产生恢复日志。

状态记录由负责该行为的模块管理，不依赖 System 执行次数判断。

## 六、日志过滤与持久化

正常运行时，宿主应默认保存自身 DEBUG、INFO、WARN、ERROR 日志。

TRACE 默认关闭，仅在开发诊断期间按需启用。

第三方依赖日志可以单独设置过滤规则，避免无关日志淹没应用诊断信息。

正式 Gallery 必须确保必要日志能够可靠保存，包括：

- 用户操作与业务结果。
- 重要程序生命周期和业务任务执行过程。
- WARN 与源头 ERROR。
- 错误处理 DEBUG 与 ECS 兜底 ERROR。

日志持久化不得采用会在缓冲区满时静默丢弃必要错误记录的配置。

Backtrace 的捕获和最终输出遵循 `rules/code.md`。

## 七、Widgetry 库的特定规则

### Plugin 注册

所有 Widgetry Plugin 必须在 `build()` 完成时记录一次 DEBUG：

`<PluginName> 注册完成`

不使用“初始化成功”等替代描述，也不重复记录内部 Resource、System、Observer、Loader 或 Cache 的注册细节。

### 正常交互与内部执行

Widgetry 库不负责记录用户业务操作。

正常 Pointer、Keyboard、Hover、Focus、Selection、Drag 等控件交互，以及普通 State 同步、Cache、Layout、Style 更新，原则上保持静默。

合法 API 调用、普通同值设置、正常资源等待、Fallback 和 Observer 目标过滤，不因其正常发生而增加日志。

只有符合 DEBUG 生命周期规则、WARN 异常规则或 ERROR 错误规则时，才记录相应日志。

不得为了日志增加持续轮询、每帧遍历或无业务意义的状态追踪。

## 八、Gallery 与业务程序的特定规则

Gallery 作为应用层示例，应遵循业务操作 INFO、程序运行 DEBUG 的区分。

具有明确应用语义的用户操作均应记录，包括演示性质的操作，而不要求具备实际商业价值。

程序自动发起的业务操作应按其语义记录，并在必要时与用户发起的操作区分。

页面切换的用户意图与程序实际状态变化分别记录，不将底层 Pointer Click 当作业务操作。

正常初始化、普通输入事件和连续交互中间状态不单独产生 INFO；确认、提交、选择等明确语义操作应记录。

日志应附着在现有业务处理路径上，不得额外增加全局输入监听、轮询系统或底层事件追踪，也不得改变原有交互与异步行为。

Gallery 自身的错误继续遵循 `rules/code.md` 的错误生命周期要求。
