# 注释与 Rustdoc 规则

## 语言

项目内人工编写的代码注释与文档注释统一使用中文。

## 声明级注释

`struct`、`enum`、`trait`、`fn`、`const` 等具有独立语义的声明应编写注释，说明：

- 它负责什么。
- 为什么存在。
- 需要调用方或维护者知道的关键语义与约束。

禁止仅把标识符名称翻译一遍作为注释。

对需要进入 rustdoc 的 API 使用 `///` / `//!` 文档注释；私有实现也应按其维护价值写清楚职责，但不要为了形式制造冗余文字。

`impl` 块本身不要求为了形式额外写注释；其方法按照函数规则处理。

## Struct 字段

结构体字段需要说明字段的实际职责和语义，尤其是字段用途无法从名称完整推断时。

禁止只写“xxx 字段”“保存 xxx”之类对名称进行机械复述的注释。

## 函数内部注释

函数内部只在以下位置写注释：

- 关键步骤。
- 非显然逻辑。
- 重要约束。
- 需要解释“为什么这样做”的地方。

禁止给普通赋值、调用、循环等显然代码添加旁白式注释。

## 测试注释

每个测试本体都应写清楚：

- 测试场景。
- 要验证的行为、不变量或回归问题。

禁止仅翻译或复述测试函数名。

测试函数内部同样只对关键步骤和非显然逻辑写注释。

## 注释位置

所有注释必须单独成行，禁止在代码同一行末尾写注释。

禁止：

```rust
let index = 0; // 当前索引
```

需要解释时应把注释放在对应代码前方。

## Rustdoc 的定位

Rustdoc 的主要职责是把公共 API 的语义直接附着在 API 上，使其他项目中的开发者或 AI 在读取依赖源码 / API 文档时能够正确理解和使用 Widgetry。

公共 API 的 rustdoc 应覆盖正确使用该 API 所必需的信息，例如：

- API 的职责。
- 重要前置条件。
- 必需 Plugin / 组件关系。
- 关键状态语义。
- 程序化修改与用户交互在行为上的差异。
- 参数中特殊值的含义。
- 其他会影响调用正确性的约束。

不要求把 rustdoc 写成完整用户手册，也不使用它承载 Stage、架构决策或开发规则。

## Doctest

禁止编写 doctest。

可以正常维护 rustdoc 文档注释，但不使用可执行文档测试作为项目测试机制。
